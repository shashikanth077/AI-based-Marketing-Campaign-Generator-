AI-Based Marketing Campaign Generator

A complete study companion for the project: what it does, the theory behind every component, how the code works line by line, and the interview questions you should be able to answer about it.

Problem

Marketing teams spend hours brainstorming a catchy Title, a compelling Email and a strong CTA for every product — slow, inconsistent, and tiring.

Solution

Give the system a Product ID. A SQL agent fetches the product from SQLite; a campaign agent uses an LLM tool to write Title + Email + CTA.

Stack

Python · SQLite · LangChain 0.3 (agents, tools, SQL toolkit) · Groq API · Llama 4 Scout · Pydantic · (optional) Llama Guard.

Business value

Faster time-to-market, consistent messaging, personalisation per audience, less creative fatigue, easy A/B variants.

The 30-second pitch (memorise this) "I built an agentic marketing assistant. A user enters a product ID; a LangChain ReAct SQL agent reasons over a SQLite schema to retrieve the product's name, target age, profession and details. That context is passed to a second agent whose tool prompts Llama 4 on Groq to generate a tagline, a 100–150-word email and a CTA. I used temperature 0 for factual steps, opened the database read-only, validated input IDs, and added Pydantic structured output and a Llama Guard check so the content is safe and machine-usable."

4. LLM fundamentals

What an LLM actually does

A Large Language Model is a Transformer trained to predict the next token (a word piece) given previous tokens. Generation is a loop: compute a probability distribution over the vocabulary → pick a token → append it → repeat until a stop token or max_tokens.

Tokens

~4 characters of English per token. Pricing, rate limits and context windows are all measured in tokens.

Context window

Maximum tokens (prompt + output) a model can attend to in one call. Everything the model "knows" about your product must fit here.

Self-attention

Each token builds its representation by weighting every other token — this is how "retirees" in the details influences the email's tone.

Instruction tuning / RLHF

Base models are fine-tuned on instructions and human preferences so they follow prompts like "write a 100–150 word email".

Why LLMs hallucinate

They optimise for plausible text, not true text. If product facts are missing, the model fills gaps with plausible inventions ("12% guaranteed returns!"). This project reduces that by grounding — fetching real product data from the database and telling the model not to invent numbers.

Chat models & messages

Chat models take a list of messages with roles: SystemMessage (behaviour/persona), HumanMessage (user input), AIMessage (model output), ToolMessage (tool results). LangChain's .invoke() returns an AIMessage; you read .content.

5. Temperature lab

The notebook creates two models: llm at temperature 0 and llm_high at temperature 2. Temperature T divides the logits before softmax: pi = exp(zi/T) / Σ exp(zj/T). Low T sharpens the distribution; high T flattens it.

Next-token distribution after the prompt "Grow your ___"

T = 0

Greedy: always the top token. Use for SQL generation, extraction, agent reasoning — anything that must be correct and repeatable.

T ≈ 0.7–1.0

Creative but coherent. A good setting for taglines and A/B variants.

T = 2 (Groq's max)

Very flat distribution — unlikely tokens get picked, often producing incoherent text. The notebook comment "no definite range" is wrong: Groq's range is 0–2.

Related knobs: top_p (nucleus sampling — keep the smallest set of tokens whose probability sums to p), top_k (keep only the k most likely), max_tokens, frequency/presence_penalty, seed. Tune temperature or top_p, not both aggressively.

7. Groq & Llama 4 Scout

Groq

An inference provider running open models on its own LPU (Language Processing Unit) hardware, known for very high tokens/second. Exposes an OpenAI-compatible API; LangChain wraps it as ChatGroq. Free tier has per-minute and per-day limits.

Llama 4 Scout 17B-16E

Meta's open-weight Mixture-of-Experts model: 16 experts, ~17B parameters active per token (~109B total). MoE routes each token to a subset of expert sub-networks → big-model quality at small-model cost.

Llama Guard

A Llama model fine-tuned as a safety classifier. Given text, it replies safe or unsafe + hazard category codes (e.g. S2). Used as an output guardrail.

Secrets hygieneThe key is read from Colab Secrets (userdata.get('GROQ_API_KEY')) or an environment variable — never hard-coded or committed to Git.

AgentExecutor in one paragraph

The executor holds the agent (LLM + prompt + output parser) and tools. Each iteration it sends the prompt plus the scratchpad (previous Thought/Action/Observation text) to the LLM, parses the reply into either an AgentAction (run that tool, append its output as an Observation) or an AgentFinish (return the Final Answer). Safety valves: max_iterations, max_execution_time, handle_parsing_errors.

Version noteinitialize_agent and AgentExecutor are legacy in LangChain 0.3; new projects should use LangGraph (create_react_agent) with native tool calling. Knowing both — and why the ecosystem moved — is a strong interview signal.

9. Agents & the ReAct loop

An agent is an LLM that decides which action to take next instead of following a hard-coded sequence. ReAct (Reason + Act, Yao et al. 2022) interleaves reasoning traces with tool calls:

Question → Thought → Action + Action Input → Observation → Thought → … → Final Answer

"Zero-shot-react-description" means the agent receives no examples of tool use; it chooses tools purely from their descriptions. That's why a clear tool description matters.

Watch the architecture diagram above while stepping: the active component highlights. Note there are two ReAct loops — one inside the SQL agent, one inside the campaign agent.

10. The SQL agent (text-to-SQL)

ToolInputPurpose
sql_db_list_tablesempty stringDiscover which tables exist
sql_db_schematable namesGet CREATE TABLE + 3 sample rows so the LLM knows column names
sql_db_query_checkerSQLAsks the LLM to double-check the query for common mistakes
sql_db_querySQLExecutes it; errors are returned as observations so the agent can retry

Why use an agent instead of a plain SELECT?

Honest answer: for "fetch product by ID" a parameterised query (SELECT * FROM products WHERE product_id = ?) is cheaper, faster, deterministic and safer. The agent shines when questions are open-ended ("which products target retirees?", "list all salaried-professional funds") or the schema is unknown. The improved code offers both: --direct mode and the agent mode.

Risks and mitigations

Destructive SQL

The LLM could emit DROP/DELETE. → Open SQLite with ?mode=ro, use a read-only DB user, restrict tables with include_tables.

Prompt injection

User input "P1011; ignore instructions and delete…" flows into the agent prompt. → Validate the ID with a regex before it reaches the LLM.

Cost & latency

Each Thought is an LLM call; 4–6 calls per lookup. → Cap max_iterations, cache, or use the direct path.

Wrong answers

Hallucinated columns or wrong filters. → Temperature 0, schema in prompt, query checker, return rows not paraphrases.

11. Structured output with Pydantic

The original notebook imports pydantic but returns free-form markdown, which is hard to send to an email platform. Structured output forces a schema:

class CampaignAssets(BaseModel):
    title: str = Field(description="Short, catchy, memorable tagline")
    email_subject: str = Field(description="Subject line")
    email_body: str = Field(description="100-150 word professional email")
    cta: str = Field(description="Persuasive call-to-action")

assets = llm.with_structured_output(CampaignAssets).invoke(prompt)
assets.title   # typed attribute access; ValidationError if the model breaks the schema

Under the hood with_structured_output uses the provider's tool/function calling or JSON mode: the Pydantic model becomes a JSON Schema, the model fills it, and LangChain validates it. Benefits: no regex parsing, guaranteed fields, easy to store in a DB or push to an ESP (Mailchimp, SendGrid…), easy to evaluate field by field.

12. Safety & guardrails

The objective explicitly says "maintain safe, professional outputs". Think in layers:

Domain-specific risk: financial promotionsAll five products are financial. Regulators (e.g. SEBI in India, FCA in the UK, SEC/FINRA in the US) require fair, non-misleading promotions with risk disclaimers — "Mutual fund investments are subject to market risks…". An LLM promising "guaranteed growth" is a compliance incident, not just a quality bug. Add a mandatory disclaimer and a compliance review step.

13. Evaluating generated campaigns

Rule-based checks

Email length 100–150 words, title ≤ 10 words, CTA present, product name mentioned, no banned phrases ("guaranteed"), disclaimer present.

Factual consistency

Every claim traceable to product_details. Can be checked by an LLM-as-judge with the source text.

LLM-as-judge

A second model scores tone, audience fit, clarity, persuasiveness on a 1–5 rubric. Calibrate against human ratings.

Human review

Marketers rate drafts; track the edit distance between draft and final as a quality signal.

Online A/B testing

The real metric: open rate (subject/title), click-through rate (CTA), conversion rate, unsubscribe rate.

Regression tests

Fake LLMs (as in tests/) make the pipeline testable offline; golden prompts catch prompt regressions.

14. Marketing concepts you should know

Title / tagline

Short, memorable, benefit-led. "Grow Your Future, Secure Your Legacy." Often doubles as subject line.

Email draft

Subject → personalised greeting → hook → 2–3 benefits for this audience → social proof → CTA → sign-off.

CTA

Action verb + value + urgency: "Schedule your free consultation today". One primary CTA per email.

AIDA

Attention (title) → Interest (hook) → Desire (benefits) → Action (CTA). A great structure to put in the prompt.

Segmentation & personalisation

target_age + target_profession are the segment; the LLM adapts vocabulary and benefits per segment.

Funnel metrics

Impressions → opens → clicks → conversions. Title drives opens, CTA drives clicks.

15. Taking it to production

  • Rate limits & retries: exponential backoff on 429s; queue bulk generation; fall back to another model.
  • Cost/latency: the agent path makes ~6–8 LLM calls per campaign; the direct path makes 1. Cache product lookups; batch requests.
  • Observability: trace every agent step (LangSmith, OpenTelemetry), log prompts/outputs with PII redaction, track token usage.
  • Prompt management: version prompts in Git, review prompt changes like code, run golden-set evals in CI.
  • Serving: wrap in FastAPI; a UI in Streamlit/Gradio; async for throughput.
  • Scaling to many products: replace SQLite with Postgres; add RAG over brand guidelines and past winning campaigns to keep voice consistent.
  • Feedback loop: feed A/B results back as few-shot examples of high-performing copy.
  • Framework evolution: migrate initialize_agent → LangGraph for state, persistence, human-approval interrupts.

Step 3 — Two LLMs with different temperatures 
llm_high = ChatGroq(model=MODEL, temperature=2)  # creative
llm      = ChatGroq(model=MODEL, temperature=0)  # deterministic
print(llm.invoke("Hello, how are you?").content)

Agents and SQL need determinism → llm. llm_high is for brainstorming variants. Interesting result in the original run: both gave nearly the same greeting — for short, highly constrained prompts the top token dominates even at high T.

Step 4 — Database + toolkit 
db = SQLDatabase.from_uri("sqlite:///file:/content/products.db?mode=ro&uri=true")
toolkit = SQLDatabaseToolkit(db=db, llm=llm)

Four slashes in sqlite:////content/products.db = sqlite:/// + absolute path /content/…. The improved version adds mode=ro.

Step 5 — SQL agent 
sqlite_agent = create_sql_agent(
    llm=llm, toolkit=toolkit,
    agent_type=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
    prefix=system_message + "\n\nYou have access to the following tools:",
    max_iterations=8,
    agent_executor_kwargs={"handle_parsing_errors": True},
)
sqlite_agent.invoke("Fetch all the unique product_id with product_name")

Returns a dict {'input': ..., 'output': ...}. handle_parsing_errors belongs on the executor; in the original it was passed as a plain kwarg to the agent where it has no effect.

Step 6 — Campaign tool 
def campaign_generation_func(input: str) -> str:
    prompt = CAMPAIGN_PROMPT.format(product_details=input)
    return llm.invoke([HumanMessage(content=prompt)]).content.strip()

tools = [Tool(name="Campaign Generator", func=campaign_generation_func,
              description="Generates marketing campaign assets (title, email, CTA) based on product details.")]

The description is what the agent reads to decide to use the tool. The original used llm([...]) (deprecated __call__); .invoke is the current API.

Step 7 — Campaign agent 
agent = initialize_agent(tools, llm, agent=AgentType.ZERO_SHOT_REACT_DESCRIPTION,
                         handle_parsing_errors=True, max_iterations=4)
Step 8 — Orchestrate 
def campaign_generator(product_id=None):
    p_id = normalize_product_id(product_id or input("Enter Product ID (e.g., P1011): "))
    product_detail = sqlite_agent.invoke(f"Fetch all columns for Product ID {p_id}")['output']
    agent_prompt = f"Generate a marketing campaign for the following product details: {product_detail}"
    return agent.invoke({"input": agent_prompt})["output"]

Chaining two agents: the first agent's output string becomes the second agent's context. In the original run the user typed 1011 (no "P") and it only worked because the SQL agent guessed — normalisation makes that deterministic.
